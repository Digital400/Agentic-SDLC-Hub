## Procedure

1. Read the approved HLD's components and data model.
2. Identify which technical layer(s) the design touches: frontend, backend, database, integration, infrastructure, testing, documentation.
3. Write one story per layer per component, naming the concrete technical deliverable.
4. Write acceptance criteria that are checkable at that layer alone (e.g. "API returns 201 with the created resource").
5. Note dependencies between layer stories explicitly (e.g. the frontend story depends on the backend story's API existing).
6. Draft the story backlog using the Output Contract below, marking every block `**Mode:** HORIZONTAL`.

## Validation Checklist

- [ ] Every story is scoped to exactly one technical layer.
- [ ] Every story names a concrete technical deliverable, not a vague task.
- [ ] Cross-layer dependencies are stated explicitly in each story's Dependencies field.
- [ ] Every story block declares `**Mode:** HORIZONTAL`.

## Output Contract

One `## Story: <title>` block per story, each containing `**Epic:**`,
`**Feature:**`, `**Mode:** HORIZONTAL`, `**Technical Areas Involved:**`
(exactly one layer), `**User Story:**` (phrased for the implementing
engineer, not an end user), `**Acceptance Criteria:**` (checklist),
`**Dependencies:**`, `**Suggested Owner Role:**`, `**Priority:**`,
`**Story Points Estimate:**`.

## Examples

### Example: Self-service password reset

**Input:** HLD with Reset Request Service, Email Notification Service,
Auth Service.

**Output:** `## Story: Add POST /auth/password-reset endpoint` with Mode
HORIZONTAL, Technical Areas Involved ("Backend"), User Story ("As a
backend developer, I want a password-reset endpoint that issues a
single-use token, so that the frontend and email service have something
to call"), Dependencies ("None — this is the foundational backend
story").
