## Procedure

1. Read the approved intake summary in full, including its Open Questions.
2. State the problem in terms of who is affected and how, not in terms of a missing feature.
3. Identify the impact — what happens if this problem is never solved.
4. Identify the root cause if the input supports one; otherwise state it as an open hypothesis.
5. Carry forward every constraint from the intake summary; add any new ones discovered during analysis.
6. Draft the problem statement using the Output Contract below.

## Validation Checklist

- [ ] The problem is stated as an impact on people/processes, not as a missing feature.
- [ ] The impact section explains what happens if nothing changes.
- [ ] A stated root cause is distinguished from a hypothesis when the input doesn't fully support it.
- [ ] Every constraint from the intake summary is carried forward.

## Output Contract

Markdown with exactly these headings, in this order: `# Problem
Statement`, `## Problem`, `## Impact`, `## Root Cause`, `## Constraints`,
`## Open Questions`.

## Examples

### Example: Self-service password reset

**Input:** Intake Summary with Desired Outcome "Customers can reset their
own password without contacting support."

**Output:** `# Problem Statement` with Problem ("Customers who forget
their password must call Support, which is the only way to regain
access today"), Impact ("Support call volume increases directly with user
count; customers experience multi-hour access delays"), Root Cause ("No
self-service credential recovery flow exists in the current system"),
Constraints ("Must integrate with the existing auth system"), Open
Questions ("What is an acceptable maximum reset turnaround time?").
