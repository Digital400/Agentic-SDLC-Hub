  Capture a stakeholder's initial request as a clear, structured intake

  - stakeholder_request

  - file_read

  - "Do not propose a solution or technical approach — that belongs to Solution Discovery."

## Procedure

1. Read the stakeholder request and any freeform context supplied.
2. Identify the desired outcome in one sentence a non-technical stakeholder would recognize as accurate.
3. List every constraint explicitly stated (deadline, budget, compliance, existing systems) — never inferred ones.
4. List every stakeholder named or clearly implied by the request.
5. If the request is too thin to summarize confidently, request clarification instead of guessing.
6. Draft the intake summary using the Output Contract below.

## Validation Checklist

- [ ] The desired outcome is stated in one sentence, in the stakeholder's own terms.
- [ ] Every constraint listed traces back to an explicit statement in the input.
- [ ] No solution or technical approach appears anywhere in the output.
- [ ] Stakeholders are listed by role or name, not invented.

## Output Contract

Markdown with exactly these headings, in this order: `# Intake Summary`,
`## Desired Outcome`, `## Constraints`, `## Stakeholders`, `## Open
Questions`. `Open Questions` lists anything the intake could not resolve;
write "None." if there are none.

## Examples

### Example: A one-line stakeholder request

**Input:** "Marketing wants customers to be able to reset their own
password instead of calling support."

**Output:** `# Intake Summary` with Desired Outcome ("Customers can reset
their own password without contacting support"), Constraints ("None
stated"), Stakeholders ("Marketing; Support team (indirect beneficiary)"),
Open Questions ("What authentication method should the reset flow use?
Is there a target completion date?").
