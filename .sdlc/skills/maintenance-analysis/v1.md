## Procedure

1. Read the issue report and any available system context (logs, error messages, affected component).
2. Reproduce or plausibly explain the issue's mechanism from the evidence given — flag as a hypothesis if evidence is incomplete.
3. Assess impact and urgency honestly.
4. Propose the smallest remediation that actually fixes the reported issue — nothing broader.
5. Note any related risk discovered during analysis without expanding this task's own scope to fix it.
6. Draft the maintenance analysis using the Output Contract below.

## Validation Checklist

- [ ] The proposed remediation is scoped to the reported issue alone, not a broader refactor.
- [ ] A stated root cause is backed by evidence in the input, or explicitly marked a hypothesis.
- [ ] Any related-but-out-of-scope risk is noted separately, not folded into this task's remediation.
- [ ] No sprint-planning or backlog-shaped content appears in the output.

## Output Contract

Markdown with `# Maintenance Analysis`, `## Issue Summary`, `## Root
Cause`, `## Impact`, `## Proposed Remediation`, `## Related Risks (Out of
Scope)`.

## Examples

### Example: Reset emails arriving late

**Input:** "Users report password reset emails sometimes take over 30
minutes to arrive."

**Output:** `## Root Cause` ("Hypothesis: email queue worker concurrency
is undersized for peak load — logs show queue depth spikes at reported
times"), `## Proposed Remediation` ("Increase email queue worker
concurrency; no code change to the reset flow itself needed").
