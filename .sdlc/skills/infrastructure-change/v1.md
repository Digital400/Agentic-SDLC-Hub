## Procedure

1. Read the approved HLD's components and the ProjectExecutionProfile's runtime_image/network_policy/allowed_paths.
2. Identify what infrastructure the design actually requires (compute, storage, networking, CI/CD pipeline steps).
3. Propose the change as declarative configuration (IaC) where the project's stack supports it, referencing environment variable NAMES only for anything secret-shaped.
4. State the network policy implications explicitly — what new outbound/inbound access, if any, this requires.
5. State rollback steps for the proposed change.
6. Draft the proposal using the Output Contract below.

## Validation Checklist

- [ ] The proposal changes only paths within the profile's allowed_paths.
- [ ] Any new network access is stated explicitly and justified against the design's actual needs.
- [ ] No secret value is hardcoded — only environment variable names are referenced.
- [ ] Rollback steps are stated, not omitted.

## Output Contract

Markdown with `# Infrastructure Change Proposal`, `## Summary`, `## 
Resources Affected`, `## Configuration Changes`, `## Network Policy
Impact`, `## Rollback Plan`, `## Risks`.

## Examples

### Example: Adding an outbound email provider

**Input:** HLD's Email Notification Service, needing to call an external
transactional email API.

**Output:** `## Network Policy Impact` — "Adds one allowed outbound
domain: api.emailprovider.example — no other network policy change
proposed." `## Configuration Changes` references `EMAIL_PROVIDER_API_KEY`
by name only, never a literal value.
