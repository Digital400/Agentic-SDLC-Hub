## Procedure

1. Read the approved solution option's Recommendation section and the constraints it inherited.
2. Identify the major components and give each a one-sentence responsibility.
3. Describe how the components interact — prefer a short bulleted flow over prose.
4. Define the high-level data model: key entities and their relationships, not a full schema.
5. State the security considerations: authentication/authorization boundaries and data sensitivity.
6. Flag any architectural decision the input doesn't resolve as an open question rather than guessing.
7. Draft the HLD using the Output Contract below.

## Validation Checklist

- [ ] Every component has a one-sentence responsibility, not a paragraph of prose.
- [ ] The data model lists entities and relationships, not full column-level detail.
- [ ] Security considerations explicitly name auth boundaries and data sensitivity.
- [ ] Every unresolved architectural decision appears under Open Questions, not silently assumed.

## Output Contract

Markdown with exactly these headings, in this order: `# High-Level Design
— <short solution name>`, `## Overview`, `## Architecture`, `## Data
Model`, `## Security Considerations`, `## Open Questions`.

## Examples

### Example: Self-service password reset

**Input:** Recommended Option — "Email-based reset link."

**Output:** `# High-Level Design — Email-Based Password Reset` with
Architecture ("Reset Request Service — issues a single-use token; Email
Notification Service — sends the reset link; Auth Service — validates the
token and updates the credential"), Data Model ("PasswordResetToken
entity, belongs to User, has an expiry"), Security Considerations ("Token
must be single-use and time-limited; reset endpoint must not leak whether
an email is registered").
