## Procedure

1. Read the approved HLD's components and data model.
2. Identify the smallest slices of user-visible value the design supports — each one usable end-to-end on its own.
3. For each slice, write a user story in "As a ... I want ... so that ..." form.
4. Write acceptance criteria specific enough that Testing can verify them without guessing.
5. Estimate story points and suggest an owner role and technical areas touched.
6. Draft the story backlog using the Output Contract below, marking every block `**Mode:** VERTICAL`.

## Validation Checklist

- [ ] Every story is independently deliverable and testable on its own.
- [ ] Every story's acceptance criteria are checkable, not vague ("works well").
- [ ] No story slices by technical layer alone — each one delivers real user value end-to-end.
- [ ] Every story block declares `**Mode:** VERTICAL`.

## Output Contract

One `## Story: <title>` block per story, each containing `**Epic:**`,
`**Feature:**`, `**Mode:** VERTICAL`, `**User Story:**`, `**Acceptance
Criteria:**` (checklist), `**Suggested Owner Role:**`, `**Technical Areas
Involved:**`, `**Priority:**`, `**Story Points Estimate:**`.

## Examples

### Example: Self-service password reset

**Input:** HLD with Reset Request Service, Email Notification Service,
Auth Service.

**Output:** `## Story: Request a password reset link` with Mode VERTICAL,
User Story ("As a locked-out user, I want to request a reset link by
email, so that I can regain access without calling support"), Acceptance
Criteria ("A reset link is emailed within 1 minute of request; the link
expires after 1 hour"), Technical Areas Involved ("Backend, Database,
Email Integration").
