## Procedure

1. Read the target story's user story and acceptance criteria, and the project HLD's relevant components/data model.
2. Define the exact API changes needed (endpoints, request/response shapes) to satisfy this story alone.
3. Define the exact DB changes needed (tables/columns/migrations), consistent with the HLD's data model.
4. Define frontend changes needed, if any, at the level of components/screens touched.
5. State business rules, validation rules, and permission rules explicitly — not left implicit.
6. State error handling behavior for each failure mode the acceptance criteria imply.
7. Write concrete test cases covering every acceptance criterion.
8. Break the design into implementation tasks small enough for one Implementation Agent run each.
9. Draft the Story LLD using the Output Contract below.

## Validation Checklist

- [ ] Every API/DB change traces back to satisfying this story's own acceptance criteria.
- [ ] Business, validation, and permission rules are stated explicitly, not implied.
- [ ] Every acceptance criterion has at least one corresponding test case.
- [ ] Implementation tasks are small enough to review individually.

## Output Contract

Markdown with exactly these headings, in this order: `Story Summary`,
`Scope`, `Out of Scope`, `API Changes`, `DB Changes`, `Frontend Changes`,
`Business Rules`, `Validation Rules`, `Permission Rules`, `Error
Handling`, `Test Cases`, `Implementation Tasks`, `Dependencies`, `Risks`.

## Examples

### Example: "Request a password reset link" story

**Input:** Story — "As a locked-out user, I want to request a reset link
by email..."; HLD's Reset Request Service.

**Output:** API Changes ("POST /auth/password-reset { email } -> 202
Accepted"), DB Changes ("password_reset_tokens table: id, user_id, token
hash, expires_at"), Test Cases ("Request with a registered email issues a
token and queues an email; request with an unregistered email still
returns 202 (no user enumeration)").
